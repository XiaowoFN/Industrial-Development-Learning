## 三、SQL 模糊查询需要掌握什么

### LIKE 的基本机制

`LIKE` 是 SQL 的模式匹配运算符，`%` 匹配任意长度字符（也包括零个），`_` 匹配恰好一个字符。

```sql
SELECT *
FROM demo_order
WHERE receiver_name LIKE '%张%';
```

常见形式：

```sql
LIKE '张%'    -- 以张开头
LIKE '%张'    -- 以张结尾
LIKE '%张%'   -- 任意位置包含张
LIKE '张_'    -- 张后面恰好一个字符
```

如果用户输入的 `%`、`_` 本身应作为普通文字搜索，应进行通配符转义。PostgreSQL 还支持 `ILIKE` 进行不区分大小写的模式匹配，具体大小写行为与数据库区域设置有关。

### 多条件“联立”查询

如果必须同时满足多个条件，使用 `AND`：

```sql
SELECT *
FROM demo_order
WHERE receiver_name LIKE '%张%'
  AND status = '待处理';
```

如果满足任意一个条件即可，使用 `OR`：

```sql
WHERE receiver_name LIKE '%张%'
   OR order_no LIKE '%A01%'
```

组合时应明确括号：

```sql
WHERE status = '待处理'
  AND (receiver_name LIKE '%张%' OR order_no LIKE '%A01%')
```

因此“联立”不等于一定使用 AND，而是要按业务要求决定全部满足、任意满足或分组组合。

### MyBatis 的动态 SQL

下面假设参数对象有 `receiverName` 和 `status`：

```xml
<select id="selectDemoOrders" resultType="DemoOrder">
    SELECT *
    FROM demo_order
    <where>
        <if test="receiverName != null and receiverName != ''">
            AND receiver_name LIKE CONCAT('%', #{receiverName}, '%')
        </if>
        <if test="status != null and status != ''">
            AND status = #{status}
        </if>
    </where>
</select>
```

`<if>` 决定是否添加条件，`<where>` 处理 WHERE 和开头多余的 AND/OR。`#{}` 是参数绑定，不能为了拼接查询内容直接改成 `${}`，后者是文本替换，可能造成 SQL 注入风险。实际项目还需要考虑空值、空白输入、通配符转义和数据库方言。

## 四、为什么只改 SQL 可能够用

```text
前端条件 → Controller → Service → Mapper → Mapper.xml → 数据库
```

如果现有 Controller、Service 和 Mapper 已经能传递所需参数，新增筛选可能只需修改 Mapper.xml。若新增了请求字段、业务校验、参数转换、返回结构或权限逻辑，则可能必须修改其他层。

本次最值得学习的是沿着实际调用链检查参数是否已经存在，而不是把“只改 SQL”当成固定答案。

## 五、前端本地过滤是不是好方案？

本次查询范围是“当前已经选中的数据”，不是整个数据库，因此本地过滤是合理且简洁的方案。

```text
左侧勾选 → selectedData（原始已选数据）
                 ├─→ 生成业务单据
                 └─→ 搜索过滤 → 当前展示数据 → 表格及行合并
```

关键是搜索只影响显示，不覆盖或删除原始业务数据。例如原始有 20 条、搜索只显示 3 条，清除条件后应恢复显示全部 20 条，后续生成单据也不应因为搜索而丢失另外 17 条。

简化的 Vue 计算属性示例：

```javascript
computed: {
  displayedData() {
    const keyword = this.searchKeyword.trim()
    if (!keyword) return this.selectedData
    return this.selectedData.filter(item =>
      (item.receiverName || '').includes(keyword)
    )
  }
}
```

这只是解释原理，不代表实际项目源码。

### 为什么合并行逻辑也要修改？

原始行例如 `A A A B B C`，搜索后可能变成 `A A C`。如果表格显示的是过滤结果，而行合并仍根据原始数组的行号或合并数量计算，就可能出现错位。展示数据与行合并计算应基于同一份当前展示数据。这是本次 AI 方案中值得学习的细节。

### 是否绝对最优？

不能直接断言。对于已经加载、数据量适中、只查询当前已选集合的场景，本地过滤通常比新增后端请求更简单。若数据量很大、存在服务端分页、需要查全库、需要服务端权限过滤或统一查询语义，则可能更适合后端查询。最终还要结合实际代码质量、性能和业务约束判断。

## 六、AI 修改过程中的问题与经验

Codex 多次遇到中文编码或补丁上下文匹配失败，随后尝试 ASCII 属性定位、精确行号、结构化文本替换和正则块替换，并在修改后复查方法、标签、样式以及辅助函数。

这说明 AI 能完成复杂编辑，但工具执行成功不等于修改一定安全。以后应注意：

- 先确认真实文件编码，避免把终端乱码误认为文件损坏。
- 限制文本或正则替换范围，不要误改其他方法。
- 查看 Git Diff，确认没有无关业务改动或意外编码变化。
- 检查标签、括号、方法体和样式块是否完整。
- 构建成功只能说明构建阶段通过，不能替代业务行为和边界测试。
