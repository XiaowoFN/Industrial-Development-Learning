# 项目记录8-业务字段扩展与页面权限控制

## 一、项目概况

本次在现有 MES 系统中增加业务字段及其数据库写入功能，同时根据登录人员的不同身份，控制能够访问的页面和使用的功能。相比普通加字段需求，权限控制涉及用户身份、可访问范围、操作能力和系统原有的权限机制，是本次主要的新难点。

主要借助 Codex 完成实现，自己负责提出需求、检查效果和反馈问题。实际代码及完整测试记录尚未提供，因此以下记录不推断具体框架配置、权限规则或已经通过的测试。

## 二、实际完成的工作

### 1. 新增业务字段

在前端增加一个业务字段，并在数据库中增加对应字段，使填写的信息通过现有后端链路写入数据库。此类任务与此前的数据接入、完整业务链路项目相似，目前已经能够较熟练地借助 AI 完成，但尚不能独立手写完整链路。

### 2. 页面及功能权限控制

本次根据不同登录人员的信息，分配相应的页面访问及可操作区域。按照目前对实现过程的理解，前端编写了一个可复用的全局方法，在进入页面时读取登录人员信息，再根据不同信息决定可用功能。

实际实现可能涉及全局方法、路由守卫、状态管理或其他机制，尚未核对源码，不能确认具体采用了哪一种，也不能仅凭前端实现认定后端授权已经完整。

### 3. 既有业务计算功能维护

在此前业务计算功能的基础上继续完成少量字段扩展与页面调整。这些任务与已有经验重复度较高，属于常见维护能力的巩固。本次以权限控制为主要新增学习点，不将零散加字段任务重复计算为多个项目。

## 三、为什么权限控制更复杂？

普通字段扩展通常沿着相对固定的链路进行：

```text
前端表单 → 请求参数 → Controller → Service → Mapper → 数据库
```

权限控制还必须回答：当前用户是谁、可以访问哪些资源、可以执行哪些操作，以及系统由谁最终判断是否允许。

例如，同一页面可能有查看、编辑、提交、审批等不同权限。能够看到一个页面，不代表一定能够执行页面上的全部操作。

## 四、前端控制与后端授权

前端可以根据当前用户的权限，控制菜单、路由、按钮和操作区域的显示或禁用，这主要用于提供合适的界面体验。

```text
获取当前登录用户的权限信息
              ↓
       判断页面或操作权限
              ↓
       控制菜单、按钮与页面
```

但前端代码和请求可以被修改或绕过，**隐藏按钮不能代替后端授权**。对于受保护的数据读取、修改、删除、审批等操作，后端仍应基于可信的登录身份和服务端权限规则进行校验。

```text
用户发起受保护的操作
          ↓
前端进行展示和交互控制
          ↓
后端识别当前登录用户
          ↓
后端检查该用户是否有相应权限
          ↓
允许执行或拒绝请求
```

不能仅依赖前端提交的角色名、用户 ID 或“是否有权限”布尔值。如果项目已经有统一权限组件，应优先沿用现有机制，而不是另外建立互不一致的判断体系。

本次没有提供完整权限代码，因此不能断言原系统缺少后端校验。后续应通过实际接口和现有权限配置确认。

## 五、需要逐步理解的权限知识

目前所说的“全局方法”，可以先理解为多个页面能够复用的一段逻辑。它实际属于哪种 Vue 机制，要通过源码确认。

后续重点认识：

- 登录人员信息从哪里获得。
- 用户、角色、权限标识之间的关系。
- 页面进入时由什么机制触发权限判断。
- 菜单可见、路由访问、按钮可用分别在哪里控制。
- 权限信息尚未加载完成时如何处理。
- 后端接口是否存在独立的授权校验。

不必现在一次性学习完整权限框架。下次可以先让 AI 指出该方法的定义位置、调用位置和数据来源，再沿着真实代码阅读。

## 六、字段写入数据库的完整链路

```text
Vue 表单字段
      ↓
JS 请求方法
      ↓
Controller 接收参数
      ↓
Service 定义业务能力
      ↓
ServiceImpl 实现业务逻辑
      ↓
Mapper 接口
      ↓
Mapper.xml 中的 SQL
      ↓
PostgreSQL
```

并非每次加字段都必须修改以上全部层。如果已有通用对象或保存逻辑，修改范围可能更小；如果涉及校验、权限、计算或返回结构，则需要根据实际链路扩展。

下一次类似任务，可以尝试先自己找到前端字段、请求参数、Java 对象和 SQL 映射，再让 AI 检查遗漏，逐渐从“会描述需求”过渡到“能理解并修改代码”。

## 八、当前学习进度与下一步

JavaSE 已学习到抽象类和接口。继续把当前面向对象基础学扎实，不因工作中出现权限问题就临时跳到复杂框架源码。

```text
JavaSE 抽象类、接口
        ↓
集合、异常、IO、Lambda / Stream 等基础
        ↓
SQL / PostgreSQL
        ↓
Spring Boot
        ↓
MyBatis
        ↓
独立完成后端业务功能
        ↓
结合真实项目深入认证与授权
```

Java 的 `interface` 与 HTTP API 接口是不同概念。前者是语言中的类型和契约，后者是系统之间的通信入口。随着 Service、ServiceImpl、Controller 和 Mapper 的学习，两者会逐渐联系起来。

权限控制先作为工作中的专题积累，不要求现在立即系统学习 RBAC、Spring Security 或完整前端权限体系。

## 十、阶段总结

本次项目的难点不在字段本身，而在于理解谁能访问什么、谁能执行什么操作，以及前端和后端如何共同完成权限控制。

目前继续学习 JavaSE 是合理的。随着接口、集合、SQL、Spring Boot 和 MyBatis 逐步掌握，之前依赖 AI 完成的业务链路会越来越容易看懂。下一阶段的目标是逐渐做到自己能定位、能解释、能修改，最终能够独立编写并验证完整功能。
